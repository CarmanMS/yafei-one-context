# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Repository Is

**one-context** is a local-first, agent-agnostic umbrella repository that provides a shared context layer across multiple independent Git repos for AI-assisted development. It models "logical monorepo" semantics without physically merging repos: centralized metadata registry, knowledge base, umbrella features, and agent roles — all adapted to Cursor / Claude Code / OpenClaw via `onecxt adapt`.

Business code lives in independent repo clones under `repos/`; this repo owns the control plane and knowledge layer only.

## Build, Install & Test

```bash
# Install CLI (editable, with dev deps)
pip install -e "./packages/one-context[dev]"

# Health check
onecxt doctor
# or: python -m one_context doctor

# Run all tests
cd packages/one-context && python -m pytest tests/ -v

# Run a single test file
cd packages/one-context && python -m pytest tests/test_adapters.py -v

# Run slow/e2e tests (consume LLM tokens, skipped by default)
cd packages/one-context && python -m pytest tests/ -v -m slow

# Validate manifests after editing
onecxt doctor
```

If `onecxt` is not on PATH, use `python -m one_context` as a portable alternative.

## Key Commands

```bash
onecxt sync                          # Clone / fast-forward registered repos
onecxt sync <repo-id>                # Sync single repo
onecxt adapt dev                     # Generate tool configs for workspace "dev"
onecxt adapt dev --dry-run           # Preview without writing
onecxt adapt dev --only cursor       # Only Cursor adapter
onecxt adapt --all                   # All workspaces
onecxt adapt-install                 # Install git hooks (auto-adapt on pull/checkout)
onecxt context export <ws-id>        # Export context package
onecxt context export <ws-id> --format markdown --compress --target-tokens 8000
onecxt repo list                     # List registered repos
onecxt workspace list                # List workspaces
onecxt agent list                    # List agents
onecxt profile list                  # List profiles
```

## Architecture (Big Picture)

Six layers, top to bottom:

1. **Registry Layer** (`meta/`) — YAML manifests: `repos.yaml` (repo registry), `workspaces.yaml` (task views), `profiles.yaml` (AI behavior specs), `agents.yaml` (agent roles with knowledge refs + artifact ownership).
2. **Working Copy Layer** (`repos/`) — Local git clones, each independent. Not committed.
3. **Knowledge Layer** (`knowledge/`) — **Restructured 2026-07-25**: now a personal Obsidian vault (科研/教学/家庭), git submodule. No longer agent guidance. Old standards/playbooks/prompts: submodule history `267c959`. <!-- TODO(skill重构): agent 规范层待迁入 skills/ 或 docs/ -->
4. **Features Layer** (`features/`) — Umbrella requirements spanning repos. Lifecycle: `spec.md` → `tech_design.md` → `test_report.md` / `mr_report.md` → `deliver.md`. Indexed in `features/INDEX.md`.
5. **Adapter Layer** (`packages/one-context/one_context/adapters/`) — Translates canonical sources into tool-specific configs (Cursor `.mdc`, Claude Code adapters+agents, OpenClaw JSON). ~60 lines per new adapter.
6. **Entry Layer** (`onecxt` CLI in `packages/one-context/`) — User-facing commands for sync, adapt, export, validation.

**Core design rule:** Write shared meaning once, adapt it many times. Never duplicate intent in vendor-specific formats when a canonical source can exist.

## Conventions

- **Profile output style:** `default-coding` profile uses `tone: minimal` (文言极简). Override with "详细说明"/"展开讲"/"step by step"/etc.
- **Conventional Commits:** `feat:`, `fix:`, `docs:`, `chore:` prefixes.
- **Python style:** 3.10+, type hints, `from __future__ import annotations`, PEP 8, lines <100 chars.
- **Personal vault:** `knowledge/` is the user's personal Obsidian vault (科研/教学/家庭). Agents may read for context but must NOT write into it without explicit user request; follow its `_meta/命名与归档规则.md` when asked to add notes.
- **Feature linking:** Use repo `id` from `meta/repos.yaml` when linking code to features. Never guess paths.
- **Adapter principle:** Adapters translate; they do not own meaning. New tool support = new adapter class inheriting `AdapterBase`, ~60 lines.
- **Skill projects:** Video topic directories should NOT copy Node scripts; use `--project <dir>` to point to material-only folders.

## Content Pipeline (video/audio features)

Content-creation features go under `features/content-pipeline/`. Use `features/_template/spec-content-pipeline.md` (not generic spec.md alone). TTS routing defaults:

- **mode: duo** (default) — dual-speaker podcast via `volc-podcast-tts action=0`, input is `production/content/00-podcast-source.md`
- **mode: solo** — single-speaker via `doubao-dialogue-tts --mono`, input is `production/content/01-script.md`
- **action=3** (verbatim dialogue) requires `tts.override_reason` AND user confirmation. Never default to action=3 just because you wrote a dual-speaker script.
