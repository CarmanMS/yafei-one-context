# Playbook: review

**子命令**：`/obsidian-knowledge review [--days N] [--dir <path>]`

**定位**：深度、周期性审查。每文档启动独立 subagent（干净上下文），含 HTTP 检查 URL 可达性，分钟级。与 `/check`（快速静态规则扫描）互补。

**日常用 `/check`；定期（每周/每月）用 `/review`。**

**前置**：读完主 `SKILL.md`。

---

## 参数

| 参数 | 说明 | 默认 |
|------|------|------|
| `--days N` | 排除 N 天内已审查的文档 | 7 |
| `--dir <path>` | 仅审查指定目录 | `knowledge/`（全量） |

---

## 流程概览

```
Phase 1: 扫描 & 筛选
  - Glob knowledge/**/*.md
  - 排除 README/_meta/各域 _MOC.md
  - 按审查时间筛选（<!-- kb-review --> 块里的"审查时间"）

Phase 2: 逐文档审查（顺序执行，避免限流）
  - 每个文档启动独立 subagent
  - 3 维度检查：来源完整性 / 来源可达性 / 格式规范性
  - 自动修正 + 追加审查记录

Phase3: 汇总报告
```

## Phase1: 扫描 & 筛选

### Step 1.1 扫描文档

```bash
find knowledge/ -name "*.md" -type f | grep -vE "(README\.md|_MOC\.md|/_meta/)"
```

### Step 1.2 按审查时间筛选

```bash
# 批量提取所有已审查文件和审查日期
grep -rn "审查时间: [0-9]\{4\}-[0-9]\{2\}-[0-9]\{2\}" knowledge/
```

**筛选逻辑**（内存计算）：
- 无审查记录 → 加入待审查
- 审查日期距今 > N 天 → 加入待审查
- 审查日期距今 ≤ N 天 → 跳过

### Step 1.3 输出筛选结果

```
📋 知识库文档审查巡检

扫描文件：42 个
跳过（7 天内已审查）：15 个
待审查：27 个

待审查文档列表：
  [1] knowledge/10-科研/算子空间理论/算子空间局部性质.md
  [2] knowledge/20-教学/2026秋-高等代数/第3章教案.md
  ...

是否开始审查？
  [y] 开始顺序审查
  [n] 取消
```

## Phase 2: 逐文档审查

**关键设计原则**：每个文档使用独立 subagent 审查，**不共享主会话上下文**，确保审查基于文档本身内容而非编写/导入时的历史。

### Subagent prompt

对每个待审查文档，启动 subagent：

```
你是知识库文档审查员。请审查以下知识文档的规范性。

## 待审查文档
文件路径: <filePath>

## 审查步骤

### Step 1: 读取文档
使用 Read 工具读取: <filePath>

### Step 2: 三维度检查

#### 维度 1: 来源完整性
- [ ] 文档是否有来源信息块（来源、作者、发布日期、收录日期）
- [ ] 外部来源文档是否包含来源信息（必填）
- [ ] 其他类型：来源选填，原创可省略，导入必填
- [ ] 是否有收录时间

来源信息格式：
  > 来源：{来源名称}
  > 作者：{原作者/组织}
  > 发布日期：{YYYY-MM-DD}
  > 收录日期：{YYYY-MM-DD}

#### 维度 2: 来源可达性

公网 URL 检查：
- [ ] 使用 Bash 执行 curl 检查 HTTP 状态码
- [ ] 2xx/3xx → ✅ 可达
- [ ] 4xx/5xx → ❌ 出处失效
- [ ] 超时/DNS 失败 → ❌ 出处失效

内网/私有 URL：
- 无法从当前环境验证 → ⚠️ 内网链接，需人工确认

本地文件路径：
- [ ] 检查引用的本地文件路径是否存在（注意本 vault 用相对 wikilink，非绝对路径）

检查范围：
- 来源信息块中声明的来源链接
- 正文中引用的关键链接（最多检查前 5 个）

#### 维度 3: 格式规范性
- [ ] 文件名是否中文自然命名（见名知义，**禁止** kebab-case / 纯英文；日志类 YYYY-MM-DD.md 例外）
- [ ] 来源信息块是否完整（外部来源必填）
- [ ] Markdown 格式正确（标题层级、表格、列表）
- [ ] 正文行数 ≥ 20 行（不含来源信息和空行）
- [ ] 工具中立性：不绑定特定平台或工具专有语法
- [ ] frontmatter 三字段完整（type / status / created）
- [ ] 标签两级且以领域开头（`#科研/...` `#教学/...` `#家庭/...`）
- [ ] 笔记至少 1 个 wikilink

### Step 3: 修正问题

可自动修正：
- 缺少来源信息字段 → 补充（来源标为"待确认"）
- 格式问题（标题层级、Markdown 语法） → 直接修正
- 缺 frontmatter 字段 → 补全 type/status/created

不可自动修正：
- 出处失效（URL 返回 4xx/5xx） → 标注失效 URL 和状态码
- 缺少来源声明 → 标注"无出处信息，需补充"
- 内网链接无法验证 → 标注"内网链接，需人工确认"
- 命名不规范（kebab-case/纯英文） → 标注建议新文件名（不执行重命名）
- 工具中立性违规 → 标注具体违规项

**最小修正原则**：自动修正时只修正确定的问题，不做"优化"或"改写"。
**禁止删除内容**：自动修正不得删除文档中的任何内容，只能补充或格式调整。

### Step 4: 追加审查记录

在文档末尾追加审查记录。如果文档已有审查记录（<!-- kb-review --> ... <!-- /kb-review -->），替换为新的审查记录。

使用 Edit 工具，在文档最末尾添加：

```markdown
<!-- kb-review -->
> 📋 审查记录
> - 审查时间: <today>
> - 审查结果: ✅通过 / ⚠️已修正 / ❌需人工处理
> - 修正简述: {具体列出修正的内容;通过则写"无问题";需人工处理则写问题摘要}
<!-- /kb-review -->
```

审查结果判定：
- ✅通过：所有维度无问题
- ⚠️已修正：发现问题但已全部自动修正
- ❌需人工处理：存在不可自动修正的问题

### 输出格式

```
📄 <filename>
来源完整性: ✅/⚠️/❌ {说明}
来源可达性: ✅/⚠️/❌ {说明}
格式规范性: ✅/⚠️/❌ {说明}
审查结果: ✅通过/⚠️已修正/❌需人工处理
修正简述: {修正内容}
```
```

### 顺序执行

逐个执行，每次只启动一个 subagent，**禁止并发**，避免限流：

```
for doc in pending_docs:
  result = subagent(prompt)  # 等待上一个完成
  print(f"📊 审查进度: {completed}/{total}")
  print(result.summary)
```

- 如需保留历史：在块内追加多个 `📋 审查记录` 段落

---

## 约束

- **顺序执行**：subagent 必须逐个顺序启动，禁止并发
- **独立上下文**：每个 subagent 必须在干净上下文中工作
- **公网 URL 做 HTTP 检查**：curl 验证可达性，记录状态码
- **内网链接宽容处理**：无法验证的私有 URL 标为"需人工确认"
- **最小修正原则**：只修正确定的问题，不做"优化"或"改写"
- **禁止删除内容**：自动修正不得删除文档中的任何内容
- **审查记录强制追加**：每个审查完成的文档必须在末尾追加审查记录
- **进度实时输出**：每完成一个文档就输出进度
- **长时间运行可接受**：用户明确知道此命令可能运行较长时间
