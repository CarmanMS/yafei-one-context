# Review

用于方案、架构、代码或科研工作流的多视角评审。默认只读；用户只要求评审时，不修改文件。

## 1. 确定范围

先确认评审对象、成功标准和允许读取的事实来源。能从仓库、清单、测试或文档查到的事实直接核实，不向用户反问。

按任务选择最少的独立视角，通常 2–4 个：

- 正确性与风险：错误、数据丢失、安全边界、缺失假设
- 架构与 YAGNI：边界、依赖、重复权威源、可删除复杂度
- 实现与验证：可执行性、失败语义、测试与跨平台行为
- 科研与可复现性：符号、证明依赖、引用、实验或计算复现

角色必须与对象相关；不要为了“委员会完整”召唤无关角色。

## 2. 并行独立评审

将相同的对象、约束和证据要求交给各 subagent。每个评审者独立输出：

```text
[P0|P1|P2] 标题
证据：文件:行号、命令结果或明确事实
影响：为什么会改变结论
建议：最小修复
```

优先级：

- P0：数据丢失、安全漏洞、核心结论错误或不可恢复失败
- P1：真实功能缺陷、不可复现、重要边界缺失或显著维护风险
- P2：不阻塞的简化、表达或文档建议

没有可定位证据的内容标为“待核实”，不得包装成事实。评审者不互相读取答案，避免同质化。

## 3. 主代理汇总

主代理负责：

1. 复核高优先级证据。
2. 合并重复项。
3. 明示评审者之间的冲突及判断依据。
4. 区分已证实问题、推断和可选建议。
5. 给出按影响排序的最小行动清单。

默认只做一轮。只有证据冲突或用户要求深入时，才对具体争议追加一轮；不做无终止条件的对弈。

## 4. 数学科研要求

涉及数学内容时单独检查：

- 定理的假设是否完整，符号和量词是否一致
- 引理依赖是否循环，证明中是否存在跳步
- 文献引用是否真的支持相应断言
- 计算实验是否给出代码、参数、随机种子和环境
- 模型生成内容是否被误称为证明或已核实文献事实

数学正确性、工程正确性和表达建议分开报告。高风险结论需要人工或权威来源最终核验。

## 5. Obsidian 上下文

默认不加载个人 vault。仅当用户明确要求引用知识库时：

1. 先读 `skills/obsidian-knowledge/SKILL.md`。
2. 只经 Obsidian Local REST API 搜索和读取必要片段。
3. 不用文件系统读取、搜索或遍历 `knowledge/**`，不向 subagent 传 API key。
4. API 或 key 不可用时报告该限制；非 vault 评审可继续。

## 6. 修改门控

若用户同时要求修复，主代理在汇总后实施最小改动并验证。subagent 不并发修改同一文件。

若用户只要求评审，交付 findings；不自动备份、生成 review_record、改写原文或创建额外模板。

## 7. 输出

先列 findings，按 P0 → P2 排序；每项带证据与最小建议。随后简述：

- 评审覆盖范围
- 已运行的验证
- 未核实或被权限阻塞的部分
- 总体结论：不合格 / 有条件合格 / 合格

没有 actionable finding 时明确写“未发现阻塞问题”，不要制造建议凑数。
